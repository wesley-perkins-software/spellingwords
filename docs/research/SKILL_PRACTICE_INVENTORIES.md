# Final Curated Practice Inventories — All 41 Canonical Skills

**Status:** Editorial/curriculum research deliverable. Continues `SKILL_PRACTICE_MODEL_RESEARCH.md`'s architectural conclusions (accepted provisionally) by authoring and screening the actual word-by-word practice inventories those conclusions assumed but did not produce. No code, frontmatter, schema, routes, `/play`, or current Skill pages are touched by this document.

**Method note:** Every inventory below was built from (1) the Skill's existing demonstration `words`, (2) every word from every Grade Unit whose `skillIds` references that Skill (per `docs/research/canonical-curriculum-and-skills-summary.md`), (3) the Skill's frozen scope boundary in `SKILLS_ARCHITECTURE.md` §3, and (4) newly generated candidates screened against the same criteria the site's own `CANONICAL_SKILL_PAGE_STANDARD.md` §8 already applies to demonstration sets. Basic word-level phonics classification (does this word contain this pattern, is this pattern regular) is treated as ordinary linguistic description needing no external citation, per that standard's own evidence ladder (§14). Etymological claims (Greek/Latin roots) are checked against the same sources the frozen architecture already verified (`SKILLS_ARCHITECTURE.md` §3's safeguard) and flagged where this document extends beyond what was previously verified.

**A note on retained vs. excluded demonstration words:** several existing demonstration words were built under the demonstration set's own (correct, narrower) screening rules and pass those rules fine — but several others turn out, on the practice-inventory-grade screening this task requires, to introduce a second untaught pattern that is fine for a single illustrative example but undesirable across an entire practice bank a child will type repeatedly. Where that happens it is called out explicitly per §8's "distracting untaught patterns" criterion. **No demonstration set, frontmatter, or page is edited by this finding** — this is a practice-inventory-only judgment.

## Data-Model Stress Test

Reassessing the prior report's implied `practiceWords: string[]` shape against the 41 finished inventories:

**A plain `practiceWords: string[]` is sufficient for 22 of 41 Skills** — every Skill marked "Flat list" or "Base+ending pairs" above works fine as a plain string array, since the pairing/ordering in this document is an editorial presentation choice (e.g., grouping ed/ing pairs adjacently) that doesn't require the data itself to encode structure; a flat array in a sensible order already conveys it, and nothing about *practicing* those words (hear it, type it) needs the structure at runtime.

**16 of 41 Skills genuinely benefit from a lightweight subgroup tag, but do not strictly require one to function.** Every Skill marked "Structured subgroups" above (CK/TCH/DGE, Silent Letters, Soft C/G, Long U Silent E, OO Words, ER/IR/UR, Multisyllabic Words, Plurals, Common Suffixes, Suffix Spelling Changes, Un-/Re- Prefixes, Common Prefixes, Greek and Latin Roots) could technically ship as a flat `string[]` and still work in `/play` — the practice engine doesn't need to know a word's subgroup to speak it and check the typed answer. The subgroup only matters for **authoring and auditing** (making sure the bank stays balanced across a rule's conditions when someone edits it later) and optionally for **session construction** (e.g., ensuring a random 10-word session from a 24-word Multisyllabic Words bank doesn't accidentally draw all 6 from one subgroup and none from another). **Recommendation: a simple parallel structure — `practiceWords: { word: string; group?: string }[]` — is enough for all 16 of these, not a deeper schema.** This is a minimal, additive refinement to the prior report's flat-array assumption, not a reversal of it.

**2 of 41 Skills (Homophones, Commonly Confused Words) genuinely cannot be represented as `practiceWords: string[]` at all**, flat or grouped. A homophone set is not a list of independent words; it is a group of spellings that share one sound, each requiring its own sentence, where the *practice item* is really "hear this sentence, spell the target word" — the unit of practice is not the word, it's the (sentence, target-word) pair, and multiple such pairs share a "set" identity for authoring/audit purposes (so an editor can see that a set covers all its members). This requires a distinct shape, e.g.:
```
practiceSets: {
  setId: string;
  items: { word: string; sentence: string }[];
}[]
```
This is a real, load-bearing structural requirement, not an editorial nicety — the practice session **cannot function correctly** for these 2 Skills without a sentence attached to each word, per §6 of the prior report and confirmed again here by every one of the 24 sentence-context specifications in §40–41 above.

**Conclusion on the data model:** the prior report's `practiceWords: string[]` proposal is correct as a *baseline* for the majority of Skills and should not be discarded, but it is not sufficient as the *only* shape across the library. The minimum model the real content actually requires is:
1. `practiceWords: string[]` for Skills with no subgroup structure (22 Skills) — or, for implementation simplicity, this can be unified with (2) below by always using the richer shape and simply omitting `group` where unneeded.
2. `practiceWords: { word: string; group?: string }[]` for Skills with internal rule/pattern subgroups (16 Skills) — optional field, not a new content identity.
3. `practiceSets: { setId: string; items: { word: string; sentence: string }[] }[]` for the 2 sentence-gated Skills only — a genuinely different shape, reflecting that these 2 Skills are a genuinely different *kind* of practice, not just a bigger word list.

No Skill in this audit required a base-word+derived-word pairing field beyond what a `group` tag already covers (e.g., "carried"/"carrying" as a documented contrast pair works fine as two same-group entries, not a special paired-field), and no Skill required a pronunciation-note field beyond what already lives in Markdown body prose today (pronunciation notes are explanatory content, not practice-session data) — the practice engine doesn't need to know a word carries a dialect note to speak and check it correctly.
